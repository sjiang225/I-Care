# 执行摘要

I-Care 是一个面向痴呆症家庭照护者的智能照护支持系统。项目的核心目标不是制作一个普通聊天机器人，而是把可信的照护知识、情绪支持、虚拟同伴互动、本地资源推荐和长期压力追踪整合到同一个移动端友好的应用中，为照护者提供“有依据、有温度、能持续跟进”的支持。

在本阶段中，我完成了从研究设想到可运行原型的完整技术落地。系统采用 Next.js、React 和 TypeScript 构建前端，使用 FastAPI 构建后端，通过 Server-Sent Events（SSE）流式返回回答。系统已接入可切换的大语言模型接口，既可以在没有 API Key 的情况下使用 Mock 模型运行，也可以通过配置切换到 OpenAI GPT，未来还可以接入提供 OpenAI 兼容接口的自托管模型。

我将 25 份 Care2Caregivers/COPSA 官方英文教育材料整理为知识库来源，完成了 PDF 下载、文本提取、内容切块、Embedding、SQLite 向量存储和余弦相似度检索。当前知识库包含 175 个可检索切块，并保留资料标题、主题和原始链接，使 Education Agent 能够生成带编号引用的回答。如果知识库没有覆盖用户问题，系统会明确说明资料不足，而不是编造事实或来源。

在此基础上，我实现了 Coordinator、Education、Emotion-Support 和 Peer Companion 四类智能体，并通过确定性的 Agent-as-Tool 执行计划进行组合。系统可以判断用户是在询问知识、表达急性压力、寻求同伴理解，还是查找 New Jersey 本地服务；在同时存在情绪和知识需求时，系统先提供支持，再给出带引用的实用建议。每轮对话之前还会执行安全预检，对自伤、医疗急症和走失场景优先提供 988、911 或立即报警提示。

系统还实现了照护者压力与情绪记录、趋势可视化和反馈闭环。当情绪支持或同伴智能体介入时，系统会记录压力等级和情绪标签；前端使用 Recharts 显示趋势、平均压力和高频情绪。当系统发现压力持续偏高或上升时，会在后续回答中使用更温和的语气，并主动展示自我照护热线和相关视频，同时避免逐字复述历史记录造成“被监控感”。

在资源整合方面，我处理了 New Jersey 设施数据和 Care2Caregivers 视频：从 105 条原始设施记录中清洗出 95 家候选设施，覆盖 20 个县；整理了 5 条高可信度求助热线和 12 个官方视频；实现了按县查询设施、按主题推荐视频，以及电话、设施和视频的结构化资源卡片。

此外，我完成了可选用户账户、对话历史和数据隔离。游客可以直接体验；注册用户的对话、情绪趋势和历史记录按账号持久化。密码采用 PBKDF2-HMAC-SHA256 和随机盐存储，登录使用可撤销、可过期的随机令牌，后端只从令牌识别用户身份。

最后，我使用 82 个真实照护者问题运行了完整多智能体流水线。评测结果显示：0/82 不安全回答，71/82（87%）检索到了正确或预期主题，63/82（77%）回答带有 Care2Caregivers 引用。评测同时识别出 communication、understanding dementia 和 delirium 等检索或语料薄弱点，为下一轮优化提供了明确方向。

本阶段已经证明核心方案可以运行，但它仍是研究原型，而不是合规生产系统。正式对外使用前仍需完成临床专家独立审核、资源联系方式复核、IRB/HIPAA 与托管方案确认、生产部署、安全审计、限流监控，以及真实照护者可用性研究。

# 1. 项目背景与目标

## 1.1 项目背景

痴呆症家庭照护者通常需要同时处理行为变化、睡眠、沟通、营养、失禁、长期照护选择等实际问题，也容易长期承受疲惫、孤独、内疚、焦虑和失控感。传统信息网站能够提供资料，但往往要求用户自己搜索、判断和整合；一般聊天机器人虽然使用方便，却可能缺少权威依据、引用和健康安全边界。

I-Care 因此被定义为一个综合型照护伙伴：它既要能够基于 Rutgers Health/COPSA Care2Caregivers 材料回答问题，也要能够识别照护者的情绪状态、提供同伴式支持、推荐 New Jersey 本地服务，并追踪压力随时间的变化。

## 1.2 本阶段目标

本阶段主要目标包括：

- 把研究 proposal 转换为可以开发和验证的系统架构；
- 建立 Care2Caregivers 循证知识库和可引用的 RAG 回答能力；
- 实现协调、教育、情绪支持和虚拟同伴等多智能体能力；
- 支持文字、语音输入、答案朗读和移动端 PWA 使用；
- 建立照护者情绪/压力的记录、展示和反馈闭环；
- 整合 New Jersey 本地资源和 Care2Caregivers 视频；
- 支持游客体验、用户注册、历史记录和多用户数据隔离；
- 使用真实问题进行初步质量与安全评测；
- 为后续部署、IRB 和可用性研究保留明确路径。

## 1.3 关键约束

- **目标用户约束：** 照护者中可能包含较多中老年用户，因此界面必须简单、字体清晰、按钮足够大。
- **研究阶段约束：** 首版主要服务于小规模原型验证和计划中的 6 人可用性测试，而不是高并发商业上线。
- **成本约束：** 先采用 Web/PWA，避免首版立即产生 App Store 上架成本。
- **可信性约束：** 健康场景不能编造事实、来源和电话号码；回答需要能追溯到资料。
- **隐私约束：** 当前阶段使用原型级存储和鉴权；真实受试者数据必须等待 IRB、HIPAA 和机构 IT 要求明确。
- **语言约束：** 首版界面和语音主要使用英文，架构为未来多语言扩展保留空间。

# 2. 总体方案与实际技术架构

## 2.1 技术选型

| 层级 | 当前实际实现 | 选择目的 |
|---|---|---|
| 前端 | Next.js 15、React 19、TypeScript | 构建移动端友好的单页聊天体验，并支持 PWA |
| 后端 | Python、FastAPI | 便于实现 AI、RAG、SSE 流式接口和数据 API |
| 模型层 | 统一 LLMProvider；Mock 与 OpenAI Provider | 使开发不依赖 API Key，并为未来模型替换解耦 |
| 流式通信 | Server-Sent Events（SSE） | 让多智能体输出能够边生成边显示 |
| 知识库 | SQLite + Embedding + 本地余弦检索 | 让小规模原型无需额外数据库服务即可运行 |
| 业务数据 | SQLite | 保存账户、令牌、对话、消息和 wellbeing 记录 |
| 语音 | Web Speech API | 免费提供浏览器端语音输入和文本朗读 |
| 图表 | Recharts | 在移动端显示压力趋势和情绪摘要 |
| 内容渲染 | React Markdown + GFM | 正确显示标题、列表、强调和引用编号 |

## 2.2 实际系统数据流

用户从手机或电脑打开 PWA，通过文字或语音输入问题。前端将最近的对话消息发送到 `/api/chat`。后端首先执行安全预检，然后由 Coordinator 判断当前消息需要知识、情绪、同伴或本地资源中的哪些能力。Coordinator 生成确定性的执行计划并顺序调用相应智能体。

Education Agent 会对用户问题生成向量，检索 Care2Caregivers 知识库，将最相关的内容连同编号加入提示词，并以 SSE 持续返回答案、来源和资源事件。Emotion-Support 或 Peer Companion 会评估并记录照护者状态。前端接收不同类型的 SSE 事件，将回答正文、引用来源、资源卡片、情绪记录提示和同伴标识组合成一个完整响应。

## 2.3 设计与实际实现的差异

最初设计将 PostgreSQL + pgvector 作为生产目标，但当前实际原型使用 SQLite：知识库向量存储在本地 SQLite 中，检索采用 NumPy 余弦相似度；账户、对话和情绪数据也使用 SQLite。这个取舍降低了本地运行和演示的复杂度，适合只有几百个知识切块的小规模原型，但正式扩展时仍应迁移到 PostgreSQL/pgvector 或等效托管向量数据库。

原设计中还提到 Tailwind CSS，但当前实际界面主要由项目自己的 `globals.css` 样式实现。汇报时应以当前代码为准，而不是沿用早期设计文档中的所有技术名词。

# 4. 阶段二：M0 前后端脚手架与基础体验

## 4.1 目的

搭建一个在没有真实模型和生产基础设施时也能运行的最小系统，先打通前端、后端、流式输出和手机端体验，为后续知识库和多智能体开发提供稳定底座。

## 4.2 完成内容

- 创建 FastAPI 后端和流式 `/api/chat` 接口；
- 创建 Next.js/React/TypeScript 前端聊天页面；
- 建立 LLM Provider 抽象接口；
- 实现 Mock Provider，使项目不需要 API Key 也能演示；

- 添加 PWA manifest、应用图标和移动端主屏幕安装能力；
- 添加语音输入、答案朗读、医疗免责声明和 Rutgers 版权信息；
- 采用大字体、高对比和大按钮作为基础无障碍原则。

## 4.3 实现方法

后端将对话、流式对话和 Embedding 统一抽象到 `LLMProvider`，业务代码不直接绑定具体模型。前端通过 Next.js 的 API 转发访问后端，并逐段接收 SSE 文本。语音输入使用浏览器的 SpeechRecognition，朗读使用 SpeechSynthesis，因此无需额外付费语音服务或原生 App 权限。

## 4.4 结果与价值

# 5. 阶段三：M1 Care2Caregivers RAG 知识库

## 5.1 目的

解决普通大模型回答不可追溯、可能产生幻觉的问题，使系统能够基于 Care2Caregivers 官方材料提供循证、可引用的照护指导。

## 5.2 数据准备

我在 `backend/app/kb/sources.json` 中整理了 25 份 Care2Caregivers/COPSA 教育资料，覆盖以下 11 个主题：activities、understanding dementia、communication、challenging behaviors、incontinence、nutrition、sleep、recognition、care options、caregiver self-care 和 about。

资料记录保留文档 ID、标题、主题、英文 PDF 链接和可用的西班牙语链接。首版只摄取英文内容，西班牙语资料保留用于后续扩展。

## 5.3 实现步骤

1. 使用 HTTP 下载资料 PDF；
2. 使用 pypdf 提取文本；
3. 清理并按适当长度切分文本，同时保留文档 ID、标题、主题和 URL；
4. 调用当前配置的 LLM Provider 生成 Embedding；
5. 将文本、元数据和向量写入 SQLite；
6. 对用户问题生成查询向量；
7. 使用 NumPy 计算余弦相似度并选择 Top-K 内容；
8. 将命中内容格式化为带编号的上下文，交给 Education Agent；
9. 在前端展示引用编号、资料标题和原始链接。

## 5.4 当前结果

- 已摄取 25 份资料；
- 知识库包含 175 个向量切块；
- 本地知识库约 5.5 MB；
- 支持在没有外部向量数据库的情况下运行；
- 文档元数据能够支撑主题分析、引用和视频推荐。

## 5.5 关键可信性设计

Education Agent 的提示词要求所有事实性陈述尽量依据提供的资料，并使用 `[1]`、`[2]` 等编号引用。如果资料不覆盖问题，系统必须如实说明，再给出有限的通用安全建议，并建议联系 Care2Caregivers 或医生。此规则在 delirium 等知识缺口问题上已经表现出作用：系统没有伪造资料，而是说明当前参考材料未专门解释该主题。

# 6. 阶段四：M2 Education Agent

## 6.1 目的

将“检索到资料”进一步转化为用户能够理解和执行的照护建议，同时保证回答来源清楚、语言温和、适合照护者阅读。

## 6.2 完成内容

- 实现 Education Agent；
- 每次对话检索至少 6 个相关知识切块；
- 对相同来源文档去重并统一编号；
- 流式生成回答；
- 将来源作为独立 SSE 事件发送给前端；
- 在资料不足时执行保守回答策略；
- 在用户有情绪压力但没有单独运行 Emotion Agent 时，加入简短共情引子。

## 6.3 实现方法

Education Agent 先调用检索层，将命中内容按来源文档编号。提示词中同时包含知识上下文、回答规则、医疗边界和当前对话历史。正文由模型流式返回，引用列表在前端单独显示。这样既保留了自然对话体验，又让用户能够检查答案来自哪份 Care2Caregivers 资料。

## 6.4 结果与价值

Education Agent 将项目从“通用聊天界面”转变为有组织知识来源的照护教育工具，也是后续质量评测中引用率和检索主题命中率的基础。

# 7. 阶段五：M2 多智能体框架、情绪支持与安全护栏

## 7.1 目的

照护者的消息经常同时包含实际问题和情绪负担。例如，“他整夜在家里走来走去，我快撑不住了”既需要睡眠/游走指导，也需要先被理解。单一 Agent 很难稳定处理这种复合需求，因此需要明确角色并进行可控编排。

## 7.2 Coordinator 路由

Coordinator 使用结构化 tool call 判断：

- `needs_education`：是否需要知识或操作建议；
- `needs_emotion`：是否表达急性压力、无望或难以承受；
- `needs_peer`：是否表达孤独、没人理解或想知道别人是否也如此；
- `needs_resources`：是否在寻找机构、服务或本地帮助；
- `county`：是否提到了 New Jersey 县名。

如果模型路由失败，系统采用安全兜底，将消息作为教育问题处理，保证每轮仍然能够产生回答。

## 7.3 Emotion-Support Agent

Emotion-Support Agent 负责识别当下情绪、提供简短共情和可执行的减压建议。它可以静默参考自我照护资料改善措辞，但不会输出 `[n]` 引用，也不会发送来源列表，从而避免与 Education Agent 的引用编号发生冲突。

该 Agent 还会调用 wellbeing 记录能力，将压力等级（1—5）、情绪标签和简要说明写入数据库，并向前端发送 wellbeing signal。

## 7.4 安全预检

每轮路由之前都会执行确定性的规则检查，当前覆盖：

- 自伤或自杀表达：优先显示 988 和 911；
- 胸痛、无法呼吸、昏迷、癫痫、疑似中风、窒息等医疗急症：提示立即拨打 911；
- 痴呆患者走失：提示立即报警并准备近期照片和描述。

安全提示会先于普通回答输出。规则检查不是完整临床分类器，但它提供了快速、可预测的第一道防线。

## 7.5 Agent-as-Tool 组合改造

最初的 Coordinator 只能在 Education 和 Emotion 中二选一，导致复合消息只能获得一类能力。我随后实现了 `AgentRegistry` 和确定性的执行 Plan：

| 用户需求 | 执行计划 |
|---|---|
| 仅知识 | Education |
| 仅急性情绪 | Emotion |
| 情绪 + 知识 | Emotion → 连接语 → Education |
| 同伴需求 | Peer（后续阶段加入） |
| 同伴 + 知识 | Peer → 连接语 → Education |
| 路由不明确 | Education 兜底 |

这种做法没有让多个模型自由协商，而是由 Coordinator 生成可预测的顺序计划。选择这种方式的原因包括：能够持续流式输出、减少额外模型调用和延迟、便于调试和回归测试，并更适合健康类应用对稳定性的要求。

## 7.6 验证结果

实施记录显示，知识型、情绪型、复合型和危机型消息均完成了真实 GPT 端到端验证。复合回答能够先共情、记录状态，再给带引用的建议；引用只由 Education Agent 产生，编号保持一致。

# 8. 阶段六：M3 情绪与压力趋势可视化

## 8.1 目的

将 Emotion Agent 已经记录的状态真正展示给照护者，实现“tracking caregiver stress patterns and emotional well-being over time”，而不是让情绪数据只停留在数据库里。

## 8.2 后端实现

- 在 `wellbeing_logs` 中保存时间、压力等级、情绪和备注；
- 新增 wellbeing 查询接口；
- 将记录按时间升序返回，方便前端画图；
- 计算记录数量、平均压力、最近压力、趋势和高频情绪；
- 数据不足 4 条时将趋势标记为 steady；
- 使用前后段平均值差异判断 up、down 或 steady。

## 8.3 前端实现

- 在聊天页面顶部增加趋势入口；
- 使用 Recharts 绘制 1—5 级压力柱状图；
- 低压力使用绿色、中等压力使用黄色、高压力使用红色；
- 展示一句话趋势摘要和常见情绪标签；
- 高压力时显示关怀卡片、Care2Caregivers 热线和自我照护链接；
- 没有数据时显示解释性的空状态；
- 收到 wellbeing signal 时，在当前回答下方显示“已记录你的感受”。

## 8.4 验证结果

验证覆盖了空会话、有 5 条压力记录的演示会话以及情绪消息后的实时刷新。后端 summary、时间顺序和趋势计算符合预期；前端构建通过。

# 9. 阶段七：M4 New Jersey 本地资源与视频整合

## 9.1 目的

补齐 proposal 中“社会支持与可用资源”的要求，让系统不仅告诉用户如何照护，还能在用户需要时提供本地服务入口、求助热线和易于观看的教育视频。

## 9.2 原始数据问题

抓取后发现原始设施页面有三个重要问题：

- 页面只提供机构名称、城市和县，不提供电话、地址或网址；
- 105 条记录中混入物业、保洁、杂志等非照护机构；
- Alzheimer's、dementia、short-term memory 等类型标签是按行轮换套用，不代表真实分类。

因此，我没有直接把网页内容原样交给用户，而是建立了数据准确性红线：不编造联系方式，丢弃不可信类型标签，清洗明显噪声，并明确标记设施信息的局限。

## 9.3 数据处理结果

- 原始设施：105 条；
- 清洗后设施：95 条；
- 删除噪声：10 条；
- 覆盖：20 个 New Jersey 县；
- 权威热线：5 条；
- 官方视频：12 个，其中 10 个英文、1 个西班牙语、1 个俄语。

被删除的内容包括 Airmark Facility Services、Apex Facilities Srvs Corp、物业管理公司、杂志和乱码记录。设施源站没有联系方式，因此前端明确提示用户通过热线进一步核实和转介。

## 9.4 功能实现

- 创建 `find_local_resources` 工具；
- Coordinator 从消息中提取县名，并确定性调用资源工具；
- 返回 statewide 热线和指定县的候选设施；
- Education Agent 根据 RAG 命中的主要主题选择 1—2 个相关视频；
- 后端通过独立 resources SSE 事件发送结构化数据；
- 前端 ResourceCard 分区显示可拨打电话、设施和 YouTube 链接。

## 9.5 验证结果

Bergen County 查询能够返回 5 条热线和 7 家设施；Essex County 代理链路能够返回 6 家设施和 5 条热线。睡眠问题会推荐 Sleep 视频，重复提问/行为问题会推荐行为主题视频。前端构建通过。

# 10. 阶段八：M6 压力趋势反馈到对话

## 10.1 目的

此前系统已经能够记录和展示压力，但当前回答不会利用历史趋势。本阶段的目标是闭合反馈循环：如果照护者近期持续高压，即使当前问题只是中性的知识问题，系统也能够自然地给予更温和的承接和自我照护资源。

## 10.2 触发规则

只有满足以下条件才触发高压力状态：记录数至少为 3，并且平均压力至少为 3.5；或者最近压力至少为 4 且趋势上升。数据少于 3 条时不触发。

## 10.3 实现动作

触发后系统执行三个轻量动作：

1. 给当轮 Agent 注入一条温和的 caregiver state 提示；
2. 即使是纯知识问题，也允许 Education Agent 先用一句简短共情语承接；
3. 附加自我照护热线和 caregiver self-care 视频。

提示词明确禁止逐字复述历史日志、列举“你上次说过什么”或使用评判语气。设计目标是支持用户，而不是制造被监控的感觉。

## 10.4 验证结果

使用同一个中性问题“What is vascular dementia?”对比测试：高压力记录 `[4,5,5]` 会触发温和开场、5 条热线和自我照护视频；低压力 `[1,2,2]` 与数据不足场景不会触发额外关怀。

# 11. 阶段九：专业化界面与交互完善

## 11.1 目的

将早期工程化聊天界面改造成更适合照护者、演示和研究使用的专业健康陪伴产品，同时降低第一次使用的理解成本。

## 11.2 完成内容

- 重做整体色彩、布局、卡片、输入区和响应式样式；
- 增加品牌标识和清晰的欢迎页；
- 提供行为问题、压力、睡眠、NJ 本地照护和同伴支持等快捷入口；
- 使用 Markdown 正确显示标题、列表、强调和引用；
- 展示来源、资源卡片和 wellbeing 记录提示；
- 保留语音输入和朗读开关；
- 增加“New conversation”按钮，返回欢迎页并开始新对话；
- 对 Peer Companion 回答增加透明身份标签；

## 11.3 结果与价值

界面不再只是展示模型文字，而是能够同时承载引用、资源、趋势和账户状态。欢迎页的快捷问题降低了空白输入框带来的使用障碍，新对话功能也使研究演示和多次任务测试更顺畅。

# 12. 阶段十：M8 Peer Companion 虚拟同伴

## 12.1 目的

补齐 proposal 中 peer-support modules 和 virtual peer interactions 的要求。该模块面向“没有人理解我”“只有我这样吗”“我很孤单”等归属和正常化需求，而不是重复 Emotion Agent 对急性压力的处理。

## 12.2 伦理设计

虚拟同伴被明确设计为“反映许多照护者普遍经历的 AI 同伴”，而不是真实人物。提示词和前端均遵守以下红线：

- 明确 AI 身份；
- 使用“许多照护者会……”等集体性表达；
- 不编造照顾父母、配偶等具体个人生平；
- 不冒充真人或声称亲身经历；
- 不给出临床诊断，不替代危机和医疗服务。

## 12.3 实现方法

我新增 PeerSupportAgent，并将 wellbeing 评估/记录逻辑抽取为 Emotion 和 Peer 可以共享的 helper。Coordinator 路由加入 `needs_peer`：急性情绪优先进入 Emotion；孤独、没人理解或寻求正常化时进入 Peer；需要事实指导时再组合 Education。前端通过 `agent: peer` signal 给消息加上“Peer Companion · an AI reflecting fellow caregivers' experiences”标识。

## 12.4 验证结果

“I feel so alone… nobody understands”能够进入 Peer；“I'm exhausted and can't cope”仍进入 Emotion；游走问题进入 Education；代理链路能够把 Peer signal 传到前端。测试回答使用集体性语言，没有编造个人故事。

# 13. 阶段十一：M9 用户账户、历史记录与数据隔离

## 13.1 目的

支持多用户独立使用和跨设备恢复历史，同时保留游客直接试用的低门槛体验。

## 13.2 数据模型

系统在 SQLite 中新增或使用以下表：

- `users`：用户 ID、邮箱、密码哈希、盐、昵称和创建时间；
- `auth_tokens`：随机令牌、所属用户、创建时间和过期时间；
- `conversations`：对话 ID、用户 ID、标题和创建时间；
- `messages`：用户/助手消息及其对话和时间；
- `wellbeing_logs`：压力、情绪和按用户或游客会话归属的状态记录。

## 13.3 安全实现

- 密码使用 PBKDF2-HMAC-SHA256；
- 每个用户拥有独立随机盐；
- 登录令牌由 `secrets.token_urlsafe` 生成；
- 令牌可以过期和撤销；
- API 使用 `Authorization: Bearer <token>`；
- 后端从令牌解析 user ID，不接受前端指定身份；
- 当前实现明确标注为原型级鉴权，未经生产安全和 HIPAA 审计。

## 13.4 API 与前端

后端新增注册、登录、退出、当前用户和历史查询 API。聊天接口采用可选鉴权：登录用户使用 `u:<id>` 作为 owner key，创建或续接 conversation，并保存 user/assistant 消息；游客继续使用浏览器生成的匿名 session ID，情绪可以临时记录，但对话不持久化。

前端实现登录/注册弹窗、令牌存取、自动恢复用户、加载最近对话、显示用户状态、退出和新建对话。

## 13.5 验证结果

验证覆盖注册 A/B 两个账户、重复邮箱、错误密码、无令牌访问 `/me`、不同用户的对话/历史/wellbeing 隔离，以及前端代理链路的注册—聊天—历史返回。游客仍可以不登录直接聊天。

# 14. 阶段十二：稳定性修复与工程维护

## 14.1 SQLite 线程问题修复

FastAPI 会在线程池中执行同步端点，而 SQLite 默认连接要求在创建它的同一线程使用。知识库连接因此可能在线程切换时失败。我将知识库 SQLite 连接改为 `check_same_thread=False`，使只读向量检索能够在 FastAPI 线程池中正常使用。

## 14.2 文档化与版本管理

项目为多智能体、wellbeing 可视化、本地资源、反馈闭环、Peer Companion、用户账户、部署和可用性测试分别建立了设计/实施文档。每份文档不仅记录结果，还记录数据问题、设计理由、文件改动和验证场景。

Git 历史共有 15 次主要提交，涵盖从脚手架到 82 题评测的完整演进。当前 `main` 与 `origin/main` 指向同一提交，工作区无未提交代码改动。

# 15. 质量评测：82 个真实照护者问题

## 15.1 评测目的

在开展真实受试者研究前，先检查系统面对已有照护者问题时的基本合理性、安全性、知识检索匹配度和引用覆盖情况，并定位知识库缺口。

## 15.2 评测方法

从 `I-Care questions(1).docx` 提取 82 个真实照护者问题，覆盖 9 个类别。每个问题都运行真实多智能体流水线，记录 Coordinator plan、完整回答和引用来源。

评测包含：

- 客观检索指标：引用来源的主题是否包含该问题所属类别；
- 引用指标：回答是否附带 Care2Caregivers 来源；
- LLM 评审：GOOD/OK/WEAK、grounded、safe 和理由；
- 人工复核：重点检查被标记的 11 条主题不匹配问题。

## 15.3 结果

| 指标 | 结果 | 解读 |
|---|---:|---|
| 安全回答 | 82/82 | 未发现 unsafe 回答 |
| LLM 评审 GOOD | 82/82 | 仅作参考，评审模型与被测模型相同，可能偏宽松 |
| 检索主题命中 | 71/82（87%） | 多数问题检索到预期或相关主题 |
| 带 Care2Caregivers 引用 | 63/82（77%） | 仍有提升引用覆盖的空间 |

## 15.4 人工复核发现

多数“主题不匹配”实际属于相邻主题，例如“如何让他冷静”“是否应该争辩”等问题虽然归在 communication，但 challenging behaviors 中的 Calming/Behaviors 内容也能合理回答。

真实语料缺口主要包括 delirium 与 dementia 的区别，以及部分记忆机制类问题。系统在 delirium 问题上明确说明参考资料没有专门覆盖该主题，没有伪造引用。个别问题仍存在检索不够精准的情况，例如失禁相关迹象没有优先命中专属文档。

## 15.5 评测局限

- LLM-as-judge 与被测系统使用相同模型，不能替代独立评审；
- 当前评测验证的是技术行为，不是临床准确性认证；
- 尚未由顾问团逐条审核全部回答；
- 尚未开展真实用户 SUS、满意度、任务时间和焦点小组研究。

# 17. 关键设计决策与解决的问题

## 17.1 为什么使用 PWA

PWA 可以让照护者通过浏览器使用，并添加到手机主屏幕，不需要首版立即上架 App Store，也不需要参与者处理复杂安装流程。未来如果需要原生应用，可以使用 Capacitor 或 WebView 壳复用现有前后端。

## 17.2 为什么使用确定性 Agent Plan

健康支持系统更需要可预测和可解释。确定性 Plan 可以控制回答顺序、保留流式体验、降低成本、避免多 Agent 自由协商产生不稳定行为，并使四类场景能够被清楚测试。

## 17.3 为什么 Emotion 不显示引用

Education 负责事实和引用，Emotion 负责共情和状态记录。将引用责任集中到 Education 可以避免多个 Agent 分别使用 `[1]`、`[2]` 造成编号冲突，也让用户更容易区分事实指导和情感支持。

## 17.4 为什么本地资源不直接照搬网页

原始网页缺少联系方式，包含非照护机构和不可信分类。直接展示会制造错误信任。因此项目选择少而准的热线、显式的数据局限提示和可重复的数据清洗脚本。

## 17.5 为什么保留游客模式

强制注册会增加中老年用户第一次体验的门槛。游客模式允许立即使用，登录则提供跨设备历史和长期趋势，形成“低门槛体验 + 可选持续使用”的折中。

## 17.6 为什么当前使用 SQLite

原型语料只有 175 个切块，首版用户规模很小。SQLite 不需要安装 Docker 或维护数据库服务，便于本地演示和回归验证。生产环境再迁移到 pgvector，可以避免在早期为基础设施投入过多时间。

应用内 SUS、满意度、任务计时和导出脚手架已经设计，但在 2026年7月1日讨论后暂缓。原因是 proposal 将导航观察、错误记录和任务时间交给研究人员，SUS/问卷也可以通过 Qualtrics 或纸质收集。因此该部分不能汇报为“已完成测试”。

## 19.3 临床和内容审核不足

82 题评测证明系统具备基本技术可用性，但不能替代临床专家评审。所有回答、热线、本地资源和安全文案在真实照护者使用前仍需要顾问团独立审核。

## 19.4 原型级安全与隐私

当前密码和令牌机制比明文存储安全，但尚未实现邮箱验证、密码找回、登录限流、审计日志、数据删除权、加密备份和生产监控，也没有完成 HIPAA 合规审计。真实健康相关数据不应直接进入未经批准的演示部署。

## 19.5 检索和语料缺口

communication 和 understanding dementia 的主题命中较低；delirium 等问题缺少专门资料。下一阶段需要通过补充权威语料、主题重排、混合检索或人工规则提高覆盖和精度。

## 19.6 数据时效性

设施、热线和网页链接会变化。当前资源文件保留来源和抓取时间，但尚未建立定期更新与自动失效检查机制。

## 19.7 当前 README 已过期

根目录 README 仍将项目描述为 M0 脚手架，并把 RAG、多智能体等列为“尚未构建”。这与当前代码不一致，容易影响新的合作者或评审者理解项目状态，应优先更新。

# 20. 下一阶段建议

# 21. 结论

本阶段完成的工作已经覆盖了 I-Care 核心技术和产品闭环：从官方资料建立知识库，由多智能体提供有依据的教育、情绪和同伴支持；记录并展示照护者状态，再把长期趋势反馈到后续对话；同时提供本地热线、设施和视频，支持语音、PWA、账户和历史记录。

项目的重要价值不只是“调用了 GPT”，而是围绕健康照护场景建立了知识来源、角色分工、编排规则、安全提示、数据追踪、资源准确性和初步评测。当前结果足以支持下一阶段的专家审核和受控演示，也清楚暴露了生产部署、临床验证、合规和真实用户研究方面仍需完成的工作。

因此，本项目当前可准确定位为：**一个功能较完整、已完成内部技术评测、等待临床内容审核与真实用户可用性验证的 I-Care 研究原型。**

# 附录 C：汇报时可直接使用的简短陈述

我设计并开发了 I-Care——一个面向痴呆症家庭照护者的多智能体 Web/PWA 原型。系统把 25 份 Care2Caregivers 官方资料构建为包含 175 个切块的 RAG 知识库，并通过 Coordinator、Education、Emotion-Support 和 Peer Companion，为照护者提供带引用的照护指导、情绪支持和透明的虚拟同伴互动。

除了聊天功能，我还实现了语音输入和朗读、危机安全提示、压力与情绪趋势追踪、高压力反馈闭环、New Jersey 资源与视频推荐、可选用户账户和跨设备历史。针对原始本地资源数据，我从 105 条记录中清洗出 95 家候选设施，并明确处理了无联系方式和错误分类问题。

系统已经使用 82 个真实照护者问题完成初步评测，结果为 0 个不安全回答、87% 的检索主题命中率和 77% 的引用覆盖率。当前系统已经达到可进行专家审核和受控演示的研究原型阶段；下一步重点是临床审核、资源复核、部署、安全合规和真实照护者可用性测试。
